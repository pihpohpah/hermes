# Какие данные реально получаются и для каких точек

Документ фиксирует фактическую проверку (не предположения) на
`2026-11-13`, provider — публичный Open-Meteo без API-ключа.

## Источники и что они отдают

| Источник | Endpoint | Что берём | Статус |
| :--- | :--- | :--- | :--- |
| Weather | `api.open-meteo.com/v1/forecast` | `temperature_2m`, `apparent_temperature`, `precipitation`, `wind_speed_10m`, `wind_gusts_10m`, `wind_direction_10m`, `relative_humidity_2m`, `cloud_cover`, `visibility`, `weather_code` | работает |
| Marine | `marine-api.open-meteo.com/v1/marine` | `wave_height`, `wave_period`, `wave_direction`, `sea_surface_temperature`, `sea_level_height_msl` | работает, **только для морских точек** |
| Air quality | `air-quality-api.open-meteo.com/v1/air-quality` | `pm2_5`, `european_aqi` | работает, отдельный источник |
| Elevation | `api.open-meteo.com/v1/elevation` | высота точки | работает, батч до 100 точек за запрос |

Единицы нормализуются: ветер приходит в км/ч, в домене хранится в м/с.

## Ключевое ограничение: сетка модели ~11 км

Open-Meteo отдаёт погоду по сетке, а не по координате. Фактические ячейки
для наших точек:

| Точка | Высота | Ячейка модели | Высота ячейки |
| :--- | ---: | :--- | ---: |
| Маяк Токаревский (sup) | 2 м | 42.988, 131.857 | 0 м |
| Мыс Вятлина (viewpoint) | 0 м | 42.988, 131.857 | 0 м |
| Мыс Тобизина (trailhead) | 42 м | 42.988, 131.857 | 94 м |
| Нагорный парк (park) | 145 м | 43.128, 131.982 | 111 м |
| Сопка Бурачка (viewpoint) | 138 м | 43.128, 131.982 | 65 м |
| Бухта Стеклянная (beach) | 3 м | 43.199, 132.045 | 0 м |

**Шесть точек → три ячейки.** Нагорный парк и Сопка Бурачка физически
разнесены и имеют разную высоту, но получают один и тот же прогноз.
Проверить это можно командой:

```bash
mise run coverage-probe            # или go run ./cmd/server coverage_probe
```

Команда печатает по каждой точке: доступность источников, какие поля
заполнены (`count/hours`), высоту точки и её источник, ячейку модели и
предупреждение `places share one model cell` для совпавших ячеек.

## Что уже сделано против этого

1. **Высота точки передаётся в запрос** (`elevation=<м>`). Модель
   пересчитывает температуру под нашу высоту — проверено: для Нагорного
   (145 м) и Бурачки (138 м) приходит разная температура, хотя ячейка одна.
2. **Высота хранится с провенансом** (`places.elevation_source`:
   `manual` / `open_meteo` / `dem`). Заполняется командой
   `mise run elevations-enrich`.
3. **Клиент видит геометрию** в ответе API (`geometry`): координаты и
   высота ячейки модели, высота точки, класс рельефа
   (`flat` / `hilly` / `mountainous`), поправка по градиенту и
   `coarse_model_notice` для холмистых и горных точек.

## Чего это не решает

- Осадки и ветер от высоты не зависят: они остаются значением ячейки.
- Региональных моделей высокого разрешения для Приморья у Open-Meteo нет
  (`icon_d2`, `arome_hd`, `hrrr`, `nbm` возвращают ошибку для этих координат).
- Поэтому для горных походов корректная формулировка: «прогноз ячейки +
  поправка на высоту», а не «прогноз на вершине».

## Горизонт и независимость источников

Данные грузятся скользящим окном «6 часов назад + сегодня + 9 дней», а не на
один календарный день. Источники независимы: отдельный запрос, отдельные
строки в `weather_observations` (`PRIMARY KEY (place_id, source, observed_at)`)
и отдельный статус в `weather_source_status`.

| Источник | Горизонт | Поля |
| :--- | :--- | :--- |
| `open_meteo_weather` | 10 дней | температура, осадки, ветер, порывы, видимость, код погоды |
| `open_meteo_marine` | 10 дней | волна, период, вода, уровень моря (только морские точки) |
| `open_meteo_air_quality` | **7 дней** | AQI, PM2.5 |

Лимит AQI (7 дней, считая сегодня) — ограничение upstream-API: `end_date` дальше
`сегодня+6` отклоняется. Поэтому AQI запрашивается своим окном, а покрытие
пишется честно (`covered_to` = последний час с данными). Проверено на живом
API:

```
weather      covered_to=2026-11-22T14:00Z  (223 ч)
marine       covered_to=2026-11-22T14:00Z  (223 ч)
air_quality  covered_to=2026-11-18T01:00Z  (114 ч)
```

`coverage_probe` и `weather_load` печатают это по каждому источнику, а API
отдаёт в поле `coverage` рядом с `sources`.

## Как посмотреть карту с рельефом

```bash
mise run map-relief-local    # собрать архив рельефа (агломерация, ~4 МБ)
mise run map-serve           # http://127.0.0.1:8080/map/ — оба режима
```

На странице переключатель **Город/Природа**: город — обычная векторная карта,
природа — растровый рельеф с дискретными высотными зонами (8–20 слоёв,
количество зависит от минимума и максимума DEM в покрытии) и 3D-объёмом
(terrain из terrarium-DEM архива, камера наклоняется) плюс вода, границы,
вершины и подписи. Сервер подключает рельеф и DEM автоматически, если
архивы собраны; без них стиль вырезает источники, чтобы MapLibre не 404-ил
несуществующие архивы: без рельефа кнопка «Природа» выключена, без DEM
природа рисуется плоско.

## Морские данные

Запрашиваются только если тип точки `sup_spot`/`beach` или слой `sea`.
Для остальных точек в `sources` пишется
`open_meteo_marine: available=false, reason="место не морское"` — это не
сбой, а отсутствие запроса. Неизвестная волна хранится как `null` и никогда
не трактуется как штиль.

## Как валидировать на всех точках карты

```bash
mise run coverage-probe                    # все точки, сегодня
mise run coverage-probe DATE=2026-11-17    # конкретный день
PLACE=<uuid> mise run coverage-probe       # одна точка
```

Для массовой загрузки точек карты (не seed-мест) точки нужно сначала
завести в `places`; `coverage_probe` рассчитан на любое их количество
(до 500 за прогон) и не требует предварительной загрузки погоды.
