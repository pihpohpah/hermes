# Минималистичные Go-тесты

Этот скилл переопределяет подход `samber/cc-skills-golang@golang-testing` для проекта hermes. Тесты здесь — редкий ресурс, а не рутина. Каждый тест должен оправдывать своё существование защитой поведения, которое нельзя сломать незаметно.

---

## 1. Философия

1. **Тестов должно быть мало.** Решение «нужен ли тест» принимается явно, а не по умолчанию. Значительная часть кода hermes — не тестируется вообще, и это нормально.
2. **Не сыпать юнитами.** Запрещено генерировать пачки тривиальных тестов («по одному на функцию»). Запрещено гнаться за процентом покрытия — coverage это инструмент поиска дыр, а не цель.
3. **Покрывать только критические места:** доменную логику со сложными условиями и инвариантами, и ветвления в usecase. Всё остальное — по явному запросу.
4. **Логика домена, не infra.** Чистые функции и правила предметной области важнее любой инфраструктуры.
5. **Формула набора:** один удачный usecase (happy path) + **2–4 пограничных случая**, которые реально меняют поведение. Если кейс не меняет результат существенно — он не нужен.

Тест — это исполняемая спецификация контракта. Тест, привязанный к внутреннему устройству, превращает каждый рефакторинг в переписывание тестов, не доказывая ничего о поведении.

---

## 2. Что тестировать, а что нет

Слои hermes (`internal/domain`, `internal/application/usecase`, `internal/infrastructure`):

| Слой | Тестировать? | Почему |
|---|---|---|
| `domain/models`, `domain/scoring` | **Да** | Чистая логика, инварианты, граничные значения — главная ценность |
| `application/usecase` | **Да** | Оркестрация с ветвлениями; ручные fakes вместо реальных зависимостей |
| Сложная SQL-логика в `infrastructure/repository` | Только если нестандартная | Тривиальные запросы и маппинг не тестировать |
| HTTP/gRPC-хендлеры-прокладки, `openmeteo`-клиенты | **Нет** | Тонкая обвязка, проверяется интеграционно/руками |
| `cmd`, DI-конструкторы, config | **Нет** | Сборка приложения, дублирующие тесты бессмысленны |

**Триггеры написания теста:**
- новая доменная логика со ветвлениями (scoring, условия, расчёты);
- usecase с осмысленным разветвлением;
- багфикс: сначала тест, воспроизводящий баг, потом исправление.

**Не писать тест на:** геттеры, конструкторы без инвариантов, тривиальные мапперы, код без ветвлений, «на всякий случай».

## 3. Базовые правила (из samber/cc-skills-golang, с минималистичным фильтром)

Каждое правило оригинального скилла получает статус: ✅ применяем как есть, ⚠️ только при явной нужде, ❌ осознанно пропускаем.

**Структура и организация — ✅ применяем:**

1. Именованные подтесты: каждый кейс таблицы — поле `name`, запуск через `t.Run(tt.name, ...)`.
2. Один `_test.go` на исходный файл (`scoring.go` → `scoring_test.go`). Исключение — очень большой файл, тогда `foo_test.go` + `foo_edgecases_test.go`.
3. Порядок тестовых функций совпадает с порядком функций в исходнике — читатель находит тест по позиции, а не поиском.
4. Именование: `TestFunc`, `TestStruct_Method`, `BenchmarkFunc`, `ExampleFunc`, `FuzzFunc` — один устоявшийся префикс, без венгерских суффиксов и `TestShould...When...`.
5. Юнит-тесты быстрые (<1 мс), детерминированные, без внешних зависимостей.
6. Тесты не зависят от порядка выполнения: каждый проходит изолированно (`go test -run TestName`), общее состояние между тестами запрещено.

**Ассерты и контракт — ✅ применяем:**

7. Ассерты только наблюдаемого поведения и публичного API, не деталей реализации — рефакторинг не должен ломать тесты, не меняющие контракт.
8. Фейкаются интерфейсы, а не конкретные типы: зависимости определяются на стороне потребителя, fake реализует именно узкий доменный интерфейс usecase.

**Изоляция и надёжность — ⚠️ только при явной нужде:**

9. `go.uber.org/goleak` (`goleak.VerifyTestMain`) — только в пакетах, порождающих собственные горутины (воркеры, подписчики). В hermes таких почти нет — не добавлять по умолчанию.
10. `testing/synctest` (Go 1.25+) — только для детерминированного тестирования кода с `time.Sleep`/тикерами/конкурентностью. Для обычной доменной логики время передавать параметром, а не подменять.
11. Фаззинг (`FuzzXxx`) — только для чистых парсеров и сериализаторов через round-trip инвариант (`Parse(Serialize(x)) == x`), с 2–3 сидовыми значениями. Не фаззить бизнес-логику.
12. `ExampleXxx` как исполняемая документация — только для публичного доменного API, где пример реально читают; это не способ поднять coverage.
13. Таймауты для потенциально зависающих тестов — только если код действительно может зависнуть (блокировки, сеть в тесте).

**Осознанно пропускаем — ❌:**

14. `t.Parallel()` — тесты маленькие и последовательные; линтер `paralleltest` в проекте отключён. Не добавлять без причины.
15. Testify и mock-фреймворки — stdlib only, `testify` в `go.mod` намеренно отсутствует.
16. Интеграционные тесты с build tag `//go:build integration` — только по явному запросу, с реальной БД через `DATABASE_URL` и т.п.
17. `httptest`-прогоны хендлеров — не пишем тесты на обвязку (см. §2), поэтому паттерны табличного тестирования HTTP не применяются.

## 4. Стандарт оформления

Проект использует **только стандартную библиотеку** — `testing` + `t.Errorf`/`t.Fatalf`.

1. **Table-driven с именованными подтестами** — см. правило 3.1.
2. **Black-box пакет** (`package scoring_test`) — тестировать публичный контракт, не приватные детали.
3. **Fakes вместо моков.** Для зависимостей usecase писать маленькие ручные структуры с методами доменных интерфейсов (см. пример ниже и `internal/application/usecase/conditions_test.go`). Никакой генерации моков.
4. **Общие хелперы** с `t.Helper()`, построители тестовых данных (см. `testHour()`, `observation(...)` в `evaluate_test.go`) — чтобы кейсы читались как спецификация.
5. Формат сообщений об ошибках: `t.Errorf("Func(%v) = %v, want %v", in, got, want)` — вход, факт, ожидание, без словесного парафраза.
6. Без `t.Parallel()` — см. правило 3.14.

## 5. Как выглядит хороший тест

```go
package usecase_test

// Ручной fake вместо мок-фреймворка: реализует доменный интерфейс,
// хранит состояние, имитирует только то поведение, которое важно сценарию.
type fakePlaces struct {
    places []models.Place
}

func (f *fakePlaces) GetByID(_ context.Context, id string) (models.Place, error) {
    for _, place := range f.places {
        if place.ID == id {
            return place, nil
        }
    }
    return models.Place{}, models.ErrNotFound
}

func TestGetPlace(t *testing.T) {
    tests := []struct {
        name    string
        id      string
        wantErr error
    }{
        {name: "happy path — existing place", id: "place-1"},
        {name: "edge — unknown id returns ErrNotFound", id: "missing", wantErr: models.ErrNotFound},
        {name: "edge — empty id returns ErrNotFound", id: "", wantErr: models.ErrNotFound},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            uc := usecase.NewGetPlace(&fakePlaces{places: []models.Place{{ID: "place-1"}}})

            place, err := uc.Handle(t.Context(), tt.id)
            if !errors.Is(err, tt.wantErr) {
                t.Fatalf("Handle(%q) error = %v, want %v", tt.id, err, tt.wantErr)
            }
            if tt.wantErr == nil && place.ID != tt.id {
                t.Errorf("Handle(%q) place.ID = %q, want %q", tt.id, place.ID, tt.id)
            }
        })
    }
}
```

Обратить внимание на живые примеры проекта:
- `internal/domain/scoring/evaluate_test.go` — построитель доменных данных + хелпер `evaluate(t, ...)`, кейсы читаются как таблица решений.
- `internal/application/usecase/conditions_test.go` — fakes `fakePlaces`, `fakeWeather` вместо репозиториев.

## 6. Анти-паттерны (запрещены)

1. **Массовая генерация тестов** по одному на каждую функцию пакета.
2. **Дублирующие кейсы** — три варианта одного и того же пути с микро-отличиями.
3. **Тесты ради coverage** — процент покрытия не является аргументом.
4. **Тесты на приватные детали** — ломаются при рефакторинге и не проверяют контракт.
5. **Моки на всё подряд** — если usecase требует пять моков, возможно, тестируется не то место.
6. **Слипы и реальное время** — если логика зависит от времени, передавать `time.Time`/часы параметром (см. правило 3.10).
7. **Порядок зависимых тестов** — каждый тест обязан проходить изолированно.
8. **Подмена библиотек ради тестов** — goleak, synctest, httptest добавляются только по правилам 3.9–3.13, а не «потому что так пишут».

## 7. Чеклист перед написанием теста

1. Это доменная логика или осмысленное ветвление в usecase? **Нет — не пишу тест.**
2. Какой один happy path защищаем? Какие 2–4 пограничных случая реально меняют поведение?
3. Укладывается ли всё в одну table-driven функцию? Если нужно две-три — точно ли все они критичны?
4. Тест проверяет контракт (что), а не реализацию (как)?
5. Кейс читается как строка спецификации? Имя подтеста — фраза про поведение: `"edge — zero quantity returns zero"`.

## 8. Запуск

```bash
go test ./...                      # все тесты
go test -run TestGetPlace ./...    # один тест
go test -run 'TestGetPlace/edge'   # подтесты по имени
go test -race ./...                # с детектором гонок
go test -cover ./...               # покрытие — только как поиск дыр
```

Тесты обязаны проходить без внешних зависимостей: никаких реальных БД, сети и env. Интеграционные тесты с `//go:build integration` — только по явному запросу.
