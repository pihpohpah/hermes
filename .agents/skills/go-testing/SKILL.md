# Минималистичные Go-тесты

Скилл заменяет для hermes подход `samber/cc-skills-golang@golang-testing`. Тест пишем, только когда он защищает
поведение, которое иначе сломается незаметно.

## 1. Философия

1. Тестов мало. Решение «нужен ли тест» принимается явно. Большая часть кода hermes без тестов, так и задумано.
2. Никаких пачек тривиальных тестов «по одному на функцию». Процент покрытия не цель: coverage помогает искать
   непокрытые ветки, и только.
3. Покрываем доменную логику со сложными условиями и инвариантами и ветвления в usecase. Остальное только по явному
   запросу.
4. Чистые функции и правила предметной области важнее инфраструктуры.
5. Набор кейсов: один happy path и 2–4 пограничных случая, которые меняют результат. Кейс, который результат не
   меняет, не нужен.

## 2. Что тестировать, а что нет

| Слой | Тестировать? | Почему |
|---|---|---|
| `domain/models`, `domain/scoring` | да | чистая логика, инварианты, граничные значения |
| `application/usecase` | да | оркестрация с ветвлениями, ручные fakes вместо зависимостей |
| `infrastructure/repository` | только нестандартную логику | тривиальные запросы и маппинг не тестируем; сборку динамического SQL проверяет `places_query_test.go` |
| HTTP-хендлеры, клиенты `openmeteo`, `eventagent` | нет | тонкая обвязка, проверяется руками или интеграционно |
| `cmd`, DI-конструкторы, config | нет | сборка приложения |

Когда тест нужен:

- новая доменная логика с ветвлениями (scoring, условия, расчёты);
- usecase с осмысленным разветвлением;
- багфикс: сначала тест, воспроизводящий баг, потом исправление.

Когда не нужен: геттеры, конструкторы без инвариантов, тривиальные мапперы, код без ветвлений, «на всякий случай».

## 3. Базовые правила (из samber/cc-skills-golang, с фильтром)

Каждое правило исходного скилла помечено: ✅ применяем, ⚠️ только при явной нужде, ❌ пропускаем.

Структура и организация, ✅:

1. Каждый кейс таблицы имеет поле `name` и запускается через `t.Run(tt.name, ...)`.
2. Один `_test.go` на исходный файл (`evaluate.go` → `evaluate_test.go`). Если файл очень большой, допустимо
   `foo_test.go` + `foo_edgecases_test.go`.
3. Тестовые функции идут в том же порядке, что и функции в исходнике, чтобы тест находился по позиции.
4. Имена: `TestFunc`, `TestStruct_Method`, `BenchmarkFunc`, `ExampleFunc`, `FuzzFunc`. Без `TestShould...When...`.
5. Юнит-тесты быстрые (меньше 1 мс), детерминированные, без внешних зависимостей.
6. Каждый тест проходит в одиночку (`go test -run TestName`), общего состояния между тестами нет.

Ассерты и контракт, ✅:

7. Проверяем наблюдаемое поведение и публичный API. Рефакторинг, который не меняет контракт, не должен ломать тесты.
8. Подменяем интерфейсы, а не конкретные типы. Fake реализует узкий интерфейс, который объявил usecase.

Изоляция и надёжность, ⚠️:

9. `go.uber.org/goleak` (`goleak.VerifyTestMain`) нужен только пакетам, которые запускают свои горутины (воркеры,
   подписчики). По умолчанию не добавлять.
10. `testing/synctest` (Go 1.25+) — только для кода с `time.Sleep`, тикерами или конкурентностью. В доменной логике
    время передаётся параметром.
11. Фаззинг (`FuzzXxx`) — только для чистых парсеров и сериализаторов через инвариант `Parse(Serialize(x)) == x`, с
    2–3 сидами. Бизнес-логику не фаззим.
12. `ExampleXxx` — только для публичного доменного API, где пример действительно читают.
13. Таймауты — только для тестов, которые могут зависнуть (блокировки, сеть).

Пропускаем, ❌:

14. `t.Parallel()`: тесты маленькие, параллельность ничего не даёт. Не добавлять без причины.
15. Testify и mock-фреймворки: только stdlib, `testify` в `go.mod` нет.
16. Интеграционные тесты пишем только по явному запросу. Образец —
    `internal/infrastructure/repository/events_import_integration_test.go`: build tag `//go:build integration`,
    запуск вручную через `go test -tags integration` против локальной тестовой базы.
17. `httptest`-прогоны хендлеров: обвязку не тестируем (см. раздел 2).

## 4. Оформление

Только стандартная библиотека: `testing`, `t.Errorf`, `t.Fatalf`.

1. Таблица кейсов с именованными подтестами (правило 1).
2. Black-box пакет (`package scoring_test`, `package usecase_test`): тестируем публичный контракт.
3. Ручные fakes вместо моков: маленькие структуры с методами нужного интерфейса, как `fakePlaces` и `fakeWeather` в
   `internal/application/usecase/conditions_test.go`. Моки не генерируем.
4. Общие хелперы помечаются `t.Helper()`. Построители данных (`testHour()`, `observation(...)` в
   `internal/domain/scoring/evaluate_test.go`) делают кейс похожим на строку спецификации.
5. Сообщение об ошибке: `t.Errorf("Func(%v) = %v, want %v", in, got, want)`. Вход, факт, ожидание, без пересказа
   словами.

## 5. Пример

```go
package usecase_test

// Ручной fake вместо мок-фреймворка: реализует интерфейс usecase,
// хранит состояние и имитирует только то, что важно сценарию.
type fakePlaceGetter struct {
	places []models.Place
}

func (f *fakePlaceGetter) GetByID(_ context.Context, id string) (models.Place, error) {
	for _, place := range f.places {
		if place.ID == id {
			return place, nil
		}
	}

	return models.Place{}, models.ErrNotFound
}

func TestGetPlaceUseCase_Do(t *testing.T) {
	tests := []struct {
		name    string
		id      string
		wantErr error
	}{
		{name: "existing place", id: "place-1"},
		{name: "unknown id returns ErrNotFound", id: "missing", wantErr: models.ErrNotFound},
		{name: "empty id returns ErrInvalidArgument", id: "", wantErr: models.ErrInvalidArgument},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			uc := usecase.NewGetPlaceUseCase(&fakePlaceGetter{places: []models.Place{{ID: "place-1"}}})

			place, err := uc.Do(t.Context(), tt.id)
			if !errors.Is(err, tt.wantErr) {
				t.Fatalf("Do(%q) error = %v, want %v", tt.id, err, tt.wantErr)
			}
			if tt.wantErr == nil && place.ID != tt.id {
				t.Errorf("Do(%q) place.ID = %q, want %q", tt.id, place.ID, tt.id)
			}
		})
	}
}
```

Живые примеры в проекте:

- `internal/domain/scoring/evaluate_test.go`: построитель доменных данных и хелпер `evaluate(t, ...)`, кейсы читаются
  как таблица решений;
- `internal/application/usecase/conditions_test.go`: fakes `fakePlaces` и `fakeWeather` вместо репозиториев.

## 6. Анти-паттерны

1. Массовая генерация тестов, по одному на каждую функцию пакета.
2. Дублирующие кейсы: три варианта одного пути с микро-отличиями.
3. Тесты ради coverage.
4. Тесты на приватные детали: они ломаются при рефакторинге и не проверяют контракт.
5. Моки на всё подряд. Если usecase требует пять подмен, скорее всего, тестируется не то место.
6. Слипы и реальное время. Время передаётся параметром (`time.Time` или функция часов), см. правило 10.
7. Тесты, зависящие от порядка запуска.
8. `goleak`, `synctest` и `httptest` «потому что так пишут». Они добавляются только по правилам 9–13.

## 7. Перед тем как писать тест

1. Это доменная логика или осмысленное ветвление в usecase? Если нет, тест не пишем.
2. Какой happy path защищаем? Какие 2–4 пограничных случая меняют поведение?
3. Укладывается ли всё в одну табличную функцию? Если нужно две-три, все ли они критичны?
4. Тест проверяет контракт (что), а не реализацию (как)?
5. Имя подтеста описывает поведение: `"unknown id returns ErrNotFound"`.

## 8. Запуск

```bash
go test ./...                                      # все тесты
go test -run TestGetPlaceUseCase_Do ./...          # один тест
go test -run 'TestGetPlaceUseCase_Do/unknown' ./...  # подтесты по имени
go test -race ./...                                # с детектором гонок
go test -cover ./...                               # покрытие, только чтобы найти непокрытые ветки
go test -tags integration ./internal/infrastructure/repository/  # интеграционные, нужна локальная БД
```

Обычные тесты проходят без внешних зависимостей: без реальной БД, сети и переменных окружения.
